# Техническое задание на разработку сайта с нуля — DocuBrain

> Полная спецификация для AI-агента/команды разработки, реализующей сайт сервиса **с нуля**.
> Документ описывает архитектуру, стек, страницы, данные, интеграции, монетизацию и дизайн-систему.
> Это исполняемый техзадание (runbook), а не только концепт — каждый раздел должен быть достаточным для старта кодирования без дополнительных уточнений.

---

## 0. Суть продукта

**DocuBrain** — RAG-бот для онбординга: корпоративный AI-ассистент по внутренним регламентам в Slack и Telegram, без риска утечки данных.

**Позиционирование:** «Корпоративный AI-ассистент по внутренним регламентам в Slack и Telegram без риска утечки данных».

**Целевая аудитория:**
- IT-компании
- Быстрорастущие агентства
- Отделы продаж
- HR-команды

**Ключевая ценность:** сотрудник задаёт вопрос про внутренний регламент прямо в Slack/Telegram — бот отвечает строго на основе загруженных корпоративных документов (RAG), без "фантазий" LLM и без передачи чувствительных данных третьим лицам сверх необходимого. HR/менеджмент видит, на какие вопросы бот не смог ответить — это сигнал о пробелах в базе знаний.

**Ключевой аргумент доверия (для B2B/enterprise-продажи):** данные каждой компании изолированы (`tenant_id`), есть вариант **On-Premises** для клиентов с строгими требованиями к безопасности данных.

## 1. Архитектура и стек

### 1.1 Компоненты системы

| Слой | Технология | Назначение |
|---|---|---|
| Frontend (маркетинг + админ-панель) | **Next.js** (App Router) + **shadcn/ui** | Публичный лендинг + панель администратора компании-клиента |
| Векторная база | **Qdrant Cloud** (основной) или **Pinecone** (альтернатива) | Хранение эмбеддингов корпоративных документов, изоляция по `tenant_id` |
| Эмбеддинги | **OpenAI Embeddings `text-embedding-3-small`** | Векторизация фрагментов документов и входящих вопросов |
| Оркестрация/бэкенд-связка | **n8n** (self-hosted или Cloud) | Пайплайн загрузки документов (chunking → embedding → запись в Qdrant) и пайплайн ответа на вопрос (retrieval → генерация) |
| LLM-генерация ответа | **GPT-4o** (или GPT-4o-mini для более дешёвых тарифов) | Сборка ответа строго по найденным фрагментам (RAG, с system-промптом "не выдумывай") |
| Источники документов | **PDF/DOCX upload**, **Notion API (OAuth)** | Загрузка/синхронизация базы знаний |
| Каналы доставки | **Slack App** (Slack App Manifest, Bot Token, Events API), **Telegram Bot API** | Точки входа сотрудников для вопросов |
| База данных (метаданные) | **PostgreSQL** (Supabase/Neon) | Компании (tenants), пользователи-админы, документы, боты, неотвеченные вопросы, подписки |
| Аутентификация | **Auth.js (NextAuth)** или **Clerk**, с поддержкой Organizations/Multi-tenant | Логин админов компании, разделение по `tenant_id` |
| Биллинг | **Stripe** (Billing/Checkout + Webhooks) для Team/Scale; ручной инвойс/договор для On-Premises | Подписки SaaS + разовый платёж |
| Хостинг frontend | **Vercel** | Деплой Next.js |
| Хостинг n8n (SaaS-режим) | **Railway/Render/VPS** | Воркфлоу-раннер, мультитенантный |
| Хостинг n8n (On-Premises) | **Сервер клиента** (Docker Compose: n8n + Qdrant self-hosted + Postgres) | Изолированный деплой для Enterprise-клиентов с требованиями к data residency |

### 1.2 Схема потока данных — загрузка базы знаний

```
[Админ компании: загружает PDF/DOCX или подключает Notion Workspace (OAuth)]
        │
        ▼
[Frontend → API: POST /api/documents (файл или Notion page ids) + tenant_id]
        │
        ▼
[n8n workflow "ingest": извлечь текст (PDF-parser / Notion API) → разбить на chunks (~500-800 токенов, overlap ~100)]
        │
        ▼
[Для каждого chunk: OpenAI Embeddings (text-embedding-3-small) → вектор]
        │
        ▼
[Qdrant: upsert вектора с metadata { tenant_id, document_id, chunk_text, source_url/page, chunk_index }]
        │
        ▼
[Обновить статус документа в БД: "проиндексирован", записать количество chunks]
```

### 1.3 Схема потока данных — ответ на вопрос сотрудника

```
[Сотрудник пишет вопрос в Slack (Events API) или Telegram (webhook)]
        │
        ▼
[n8n workflow "query": определить tenant_id по chat_id/workspace_id/bot_token]
        │
        ▼
[OpenAI Embeddings: векторизовать вопрос сотрудника]
        │
        ▼
[Qdrant: search top-K (например K=5) ближайших chunks с фильтром tenant_id]
        │
        ▼
[Если максимальный score ниже порога релевантности (например < 0.75):
    → записать в unanswered_questions (сигнал для HR/аналитики)
    → ответить пользователю: "Не нашёл точного ответа в базе знаний, передал вопрос HR/администратору"]
        │
        ▼ (если релевантные chunks найдены)
[GPT-4o: system-промпт (см. 1.4) + top-K chunks как контекст + вопрос сотрудника → сгенерировать ответ]
        │
        ▼
[Отправить ответ обратно в Slack/Telegram + записать в query_logs (для аналитики, без хранения лишних PII при необходимости)]
```

### 1.4 System-промпт для генерации ответа (эталон, использовать в n8n LLM-ноде)

```
Ты — корпоративный ассистент компании {{company_name}}. Отвечай на вопросы сотрудников
СТРОГО на основе предоставленных фрагментов внутренних документов ниже.

Правила:
1. Если ответ есть в предоставленных фрагментах — дай точный, короткий ответ на русском (или языке вопроса),
   сославшись на документ/раздел, если это уместно.
2. Если предоставленных фрагментов недостаточно, чтобы уверенно ответить — честно скажи:
   "Не нашёл точного ответа в базе знаний по этому вопросу. Рекомендую уточнить у HR/руководителя."
   НЕ придумывай информацию, которой нет в контексте.
3. Не используй внешние знания, не относящиеся к предоставленному контексту.
4. Будь кратким и деловым — сотрудники ценят время.

Контекст (фрагменты внутренних документов):
{{retrieved_chunks}}

Вопрос сотрудника: {{user_question}}
```

## 2. Модель данных (схема БД)

```sql
-- Компании-клиенты (tenants)
CREATE TABLE tenants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  plan TEXT NOT NULL DEFAULT 'team', -- team | scale | on_premises
  plan_status TEXT NOT NULL DEFAULT 'trialing', -- trialing | active | past_due | canceled
  stripe_customer_id TEXT,
  stripe_subscription_id TEXT,
  is_on_premises BOOLEAN DEFAULT false,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Админы/пользователи панели (принадлежат tenant)
CREATE TABLE admin_users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT,
  role TEXT NOT NULL DEFAULT 'admin', -- admin | viewer
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Загруженные документы (источники базы знаний)
CREATE TABLE documents (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  source_type TEXT NOT NULL, -- pdf | docx | notion
  title TEXT NOT NULL,
  source_url TEXT, -- ссылка на Notion-страницу, если применимо
  file_url TEXT, -- ссылка на загруженный файл (S3/Storage), если применимо
  status TEXT NOT NULL DEFAULT 'processing', -- processing | indexed | failed
  chunk_count INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Подключённые каналы (Slack/Telegram) на tenant
CREATE TABLE bot_channels (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  channel_type TEXT NOT NULL, -- slack | telegram
  slack_team_id TEXT,
  slack_bot_token_encrypted TEXT,
  telegram_bot_token_encrypted TEXT,
  is_active BOOLEAN DEFAULT true,
  connected_at TIMESTAMPTZ DEFAULT now()
);

-- Логи вопросов (для аналитики)
CREATE TABLE query_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  channel_type TEXT NOT NULL, -- slack | telegram
  question_text TEXT NOT NULL,
  answer_text TEXT,
  matched_document_ids UUID[],
  relevance_score NUMERIC(4,3),
  was_answered BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Неотвеченные вопросы (сигнал для HR — пробелы в базе знаний)
CREATE TABLE unanswered_questions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID REFERENCES tenants(id) ON DELETE CASCADE,
  question_text TEXT NOT NULL,
  frequency INT DEFAULT 1, -- если похожий вопрос повторяется, увеличивать
  status TEXT NOT NULL DEFAULT 'open', -- open | resolved (HR добавил документ/ответ)
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Индексы
CREATE INDEX idx_documents_tenant ON documents(tenant_id);
CREATE INDEX idx_query_logs_tenant_created ON query_logs(tenant_id, created_at DESC);
CREATE INDEX idx_unanswered_tenant_status ON unanswered_questions(tenant_id, status);
```

**Важно про изоляцию данных:** каждый вектор в Qdrant/Pinecone должен содержать `metadata.tenant_id`, и **все** поисковые запросы обязаны включать фильтр `tenant_id = current_tenant`, чтобы исключить утечку данных между компаниями-клиентами. Это критично для позиционирования "без риска утечки данных" — зафиксировать как security-инвариант, покрыть тестом.

## 3. Тарифы и лимиты (B2B SaaS)

| Тариф | Цена | Ботов | Активных сотрудников | Документов | Каналы | Аналитика |
|---|---|---|---|---|---|---|
| **Team** | $99/мес | 1 | до 25 | до 50 | Slack ИЛИ Telegram (один канал) | Базовый список неотвеченных вопросов |
| **Scale** | $249/мес | несколько (уточнить лимит, по умолчанию до 3) | до 100 | без строгого лимита (fair use) | Slack И Telegram одновременно | Глубокая аналитика пробелов в базе знаний (тренды, частота, темы) |
| **On-Premises** | $1 500 разово | без лимита | без лимита | без лимита | любые, деплой на инфраструктуре клиента | Полный доступ, данные не покидают инфраструктуру клиента |

### 3.1 Реализация лимитов (бизнес-логика)

- Лимит документов: при загрузке — проверка `COUNT(documents WHERE tenant_id = X) < limit_by_plan(tenant.plan)`. При превышении — блокировать загрузку, показывать upgrade-модалку.
- Лимит "активных сотрудников" — считать по уникальным `chat_id`/`slack_user_id`, обратившимся к боту за последние 30 дней (`DISTINCT user identifier` в `query_logs`). При приближении к лимиту — предупреждение в панели администратора.
- Ограничение каналов на Team — в UI раздела "Подключить бота" разрешить активировать только один из двух каналов (Slack ИЛИ Telegram), при попытке подключить второй — предложение перейти на Scale.
- Глубокая аналитика (Scale) — доступ к разделу `/app/analytics/insights` (тренды по темам вопросов, тепловая карта пробелов) закрыт для Team (показывать блокирующий оверлей с CTA upgrade).
- On-Premises — не через обычный SaaS-биллинг; в панели — отдельный флаг `is_on_premises`, генерация Docker Compose конфигурации (n8n + Qdrant self-hosted + Postgres) и инструкции по деплою, продажа через ручной контакт с командой (форма "Запросить деплой", а не самостоятельный Stripe Checkout).
- Биллинг Team/Scale — Stripe Checkout (subscription), Stripe Webhook обновляет `plan`/`plan_status` в `tenants`.

## 5. Детальная спецификация MVP-интерфейса

### 5.1 `/app/knowledge-base` — База знаний

**Элементы:**
- Заголовок + кнопка **"+ Загрузить документ"** и кнопка **"Подключить Notion"** (обе primary/secondary, справа сверху).
- Таблица документов:
  | Название | Тип | Статус | Кол-во фрагментов | Дата загрузки | Действия |
  - "Статус" — badge: `Обрабатывается` (с спиннером), `Проиндексирован` (зелёный), `Ошибка` (красный, с tooltip причины).
  - "Действия" — иконки: переиндексировать, удалить (с подтверждением — удаление также убирает вектора из Qdrant по `document_id`).
- Индикатор лимита: "32 из 50 документов использовано" (progress bar), при достижении лимита — CTA "Улучшить тариф".
- Пустое состояние: иллюстрация + "Загрузите первый регламент, чтобы бот начал отвечать на вопросы сотрудников" + CTA.

**Модалка загрузки документа:**
- Drag-and-drop зона для PDF/DOCX (валидация формата и размера, например до 20MB).
- Прогресс-бар загрузки → после аплоада статус переключается на "Обрабатывается" (асинхронный ingest-пайплайн в n8n).
- Кнопка "Подключить Notion Workspace" — OAuth-флоу (redirect на Notion authorize URL), после коннекта — выбор конкретных страниц/баз для индексации (мультиселект дерева страниц).

### 5.2 `/app/bots` — Подключение ботов

- Две карточки: **Slack** и **Telegram**.
- **Slack-карточка:**
  - Кнопка "Подключить Slack" → инициирует Slack App Manifest install flow (`https://slack.com/oauth/v2/authorize?...`), после установки — сохранение `slack_team_id` + `bot_token` (encrypted) в `bot_channels`.
  - После подключения: статус "✅ Подключено к workspace {team_name}", кнопка "Отключить".
- **Telegram-карточка:**
  - Поле ввода "Bot Token" (пользователь создаёт бота через @BotFather и вставляет токен).
  - Кнопка "Сохранить и активировать" → валидация токена через Telegram API `getMe`, сохранение (encrypted) в `bot_channels`, регистрация webhook.
  - После подключения: статус "✅ Бот @{bot_username} активен", кнопка "Отправить тестовый вопрос".
- Ограничение по тарифу Team: если один канал уже активен — второй показывает overlay "Доступно на тарифе Scale".

### 5.3 `/app/analytics` — Аналитика (неотвеченные вопросы)

- Заголовок + краткое пояснение: "Вопросы, на которые бот не смог ответить — это сигнал, что в базе знаний не хватает регламента."
- Таблица/лента:
  | Вопрос | Частота | Дата первого/последнего вопроса | Статус | Действие |
  - "Частота" — сколько раз похожий вопрос задавали (агрегация похожих формулировок, если реализовано — через сравнение эмбеддингов вопросов с порогом схожести).
  - "Действие" — кнопка "Отметить решённым" (после того как HR добавил соответствующий документ), кнопка "Загрузить документ по этому вопросу" (шорткат на `/app/knowledge-base/upload`).
- Фильтр: "Открытые" / "Решённые".
- Пустое состояние: "Пока нет неотвеченных вопросов — база знаний покрывает все запросы сотрудников."

### 5.4 `/app/analytics/insights` (Scale/On-Premises only)

- Блокирующий оверлей для Team-тарифа с CTA upgrade.
- Для Scale/On-Premises: графики "Топ тем вопросов" (bar chart), "Динамика неотвеченных вопросов во времени" (line chart), "Покрытие базы знаний по отделам" (если документы тегированы по отделу — опционально в v2).

### 5.5 `/app/settings/billing`

- Текущий тариф + статус + дата следующего списания.
- Таблица сравнения тарифов (раздел 3) с кнопками перехода (Stripe Checkout для Team/Scale).
- Для On-Premises — блок "Запросить деплой на своей инфраструктуре" → форма контакта с отделом продаж (не самостоятельный Checkout).

## 6. Публичный лендинг — структура и дизайн

### 6.1 Секции главной страницы

1. **Header** — логотип, навигация (Как работает / Безопасность / Тарифы), кнопки "Войти" / "Запросить демо".
2. **Hero** — заголовок в духе "AI-ассистент, который знает все ваши регламенты — и никогда не выдумывает ответ", подзаголовок про Slack/Telegram + защиту данных, CTA "Запросить демо" / "Начать бесплатно". Визуализация — имитация диалога в Slack: сотрудник спрашивает про отпуск/регламент, бот отвечает со ссылкой на документ.
3. **Как это работает** — 3 шага: Загрузите документы (PDF/Notion) → AI разбивает и индексирует базу знаний → Сотрудники получают точные ответы в Slack/Telegram.
4. **Безопасность данных** (отдельный акцентный блок, критично для B2B-доверия) — изоляция по компаниям (tenant), опция On-Premises деплоя, отсутствие "выдумывания" ответов (строго по документам), шифрование токенов интеграций.
5. **Для кого** — карточки персон: IT-компании, быстрорастущие агентства, отделы продаж, HR-команды — с конкретным примером use-case для каждой (например, HR — "онбординг новых сотрудников без нагрузки на HR-менеджера").
6. **Аналитика пробелов** — отдельный блок, демонстрирующий экран "Аналитика" как уникальную фичу (не просто чат-бот, а инструмент улучшения базы знаний).
7. **Тарифы** — 3 карточки (Team/Scale/On-Premises), Scale выделен как "популярный" для растущих команд, On-Premises — с кнопкой "Связаться с отделом продаж" вместо самостоятельной оплаты.
8. **FAQ** — аккордеон: "Куда попадают наши данные?", "Может ли бот выдумать ответ?", "Поддерживается ли Notion?", "Что входит в On-Premises?".
9. **Финальный CTA** — "Освободите HR и поддержку от повторяющихся вопросов" + кнопка "Запросить демо".
10. **Footer** — ссылки, контакты, соцсети, копирайт.

### 6.2 Дизайн-система (лендинг + панель администратора)

**Стиль:** корпоративный, надёжный, "enterprise-grade" — сдержанная технологичность, акцент на доверии и безопасности (аудитория — IT/HR/продажи в B2B, ценят чистоту и деловой вид, не "хайповый" стартап-стиль). Светлая или тёмная тема — рекомендуется **светлая основная тема** с тёмным вариантом (toggle), так как enterprise-панели администратора чаще предпочитают светлый режим для длительной работы с документами.

**Палитра:**
| Роль | Цвет |
|---|---|
| Фон основной (светлая тема) | `#FAFAFB` |
| Фон карточек | `#FFFFFF` с `border: 1px solid #E5E7EB` |
| Фон тёмной темы (альтернатива) | `#0F1117` |
| Акцент основной (brain/AI, синий-индиго — надёжность + интеллект) | `#4338CA` |
| Акцент вторичный (успех/безопасность, зелёный) | `#16A34A` |
| Акцент предупреждения (неотвеченные вопросы) | `#F59E0B` |
| Текст основной | `#111827` (светлая тема) / `#F3F4F6` (тёмная) |
| Текст вторичный | `#6B7280` |

**Типографика:** заголовки — **Inter Tight** / **Sora** (весом 600-700, деловой, не игривый), текст — **Inter**. Для технических деталей (токены, ID, код) — **JetBrains Mono**.

**Ключевой визуальный мотив:** «мозг/нейросеть документов» — стилизованная иконография узлов-связей (граф), символизирующая связывание документов в единую базу знаний; используется как декоративный элемент в hero и как loading-индикатор во время индексации документов.

**Анимации (сдержанные, enterprise-подходящие — надёжность важнее "вау-эффекта"):**
- Hero: имитация Slack/Telegram-диалога — сообщения появляются по очереди (fade-in + slight slide-up, stagger 0.3s), с "печатающимся" индикатором перед ответом бота (три точки), создающим ощущение живого ответа.
- Декоративный граф-узлов на фоне hero — статичный или с очень медленной пульсацией связей (`opacity` 0.4↔0.7, 4s ease-in-out infinite), без резких движений.
- Секция "Как это работает" — карточки шагов появляются при скролле (fade-up, stagger 0.15s), без 3D-эффектов (сдержанность).
- Блок "Безопасность данных" — иконка щита/замка с лёгкой анимацией "подтверждения" (galочка/пульс) при попадании в viewport — визуально усиливает доверие.
- Карточки тарифов — стандартный hover-lift (`translateY(-4px)`, тень усиливается), без агрессивных эффектов.
- В панели администратора: статус документа "Обрабатывается" — анимированный spinner/progress, при завершении — плавная смена на зелёный чекмарк (`scale` bounce небольшой амплитуды).
- Общее: избегать параллакса и ярких неоновых glow-эффектов (не подходит tone of voice enterprise B2B); допустимы только плавные fade/slide-переходы и smooth scroll.

**Библиотеки:** Framer Motion для UI-микроанимаций (нативно с Next.js), без обязательного GSAP — анимационная нагрузка здесь легче, чем в consumer-продуктах.

## 7. Нефункциональные требования

- **Безопасность данных (центральный приоритет продукта):**
  - Строгая изоляция по `tenant_id` на уровне всех запросов к Qdrant/Pinecone и Postgres (row-level security в Postgres, обязательный фильтр в векторных запросах) — покрыть автоматическими тестами на "cross-tenant leak".
  - Шифрование хранимых токенов (Slack Bot Token, Telegram Bot Token) в БД (например через `pgcrypto` или KMS).
  - Опция On-Premises — полностью изолированный деплой без передачи данных во внешние SaaS-сервисы компании (документация по self-hosted Qdrant + n8n).
  - Логирование доступа к документам/векторам для аудита (кто/когда индексировал, кто/когда искал).
- **Надёжность ingest-пайплайна:** retry при ошибках парсинга PDF/Notion API, уведомление админа при статусе `failed`, лимиты на размер файла и таймауты обработки.
- **Точность RAG:** порог релевантности (similarity threshold) для решения "отвечать / не отвечать", логирование `relevance_score` для последующей калибровки; периодическая переоценка порога на реальных данных.
- **Масштабируемость:** батчинг embedding-запросов при массовой загрузке документов, очередь обработки в n8n (не блокировать UI на время индексации — асинхронный статус).
- **SEO:** лендинг — SSR/ISR, метатеги, OpenGraph, `sitemap.xml`.
- **Производительность фронтенда:** LCP < 2.5s на лендинге, ленивая загрузка тяжёлых компонентов панели (таблицы документов — виртуализация при больших списках).
- **Доступность:** контраст ≥ 4.5:1, полная навигация с клавиатуры, читаемые статусы для скринридеров (не только цвет для передачи статуса — добавлять текст/иконку).
- **Комплаенс (продать enterprise-клиентам):** подготовить страницу/раздел про соответствие GDPR-подобным требованиям, политику хранения данных, возможность полного удаления данных компании по запросу (`DELETE tenant cascade` + очистка векторов в Qdrant).

## 10. Что явно НЕ входит в MVP (backlog v2)

- Поддержка дополнительных источников базы знаний (Google Docs, Confluence).
- Мультиязычные ответы с автоопределением языка сотрудника (в MVP — базовая поддержка через промпт).
- Ролевой доступ к разделам базы знаний (например, документы только для отдела продаж) — тегирование по отделам.
- Автоматическая генерация нового документа/FAQ на основе часто повторяющихся неотвеченных вопросов (AI-предложение контента для HR).
- Web-виджет чата (встраиваемый на внутренний портал компании) как третий канал, помимо Slack/Telegram.
- White-label версия для реселлеров/партнёров.
